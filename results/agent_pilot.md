## 1. What this run actually verified

- **End-to-end execution.** 12 KEEP tasks × 2 arms = 24 task-arm runs
  completed through the full pipeline: buggy source → stub "fix" →
  `check_patch` pre-check → `check_bmc` formal ladder → verdict →
  `trajectory.json` written to disk.
- **A real bug, found by running this for the first time against a
  fresh output directory.** `loop.py`'s success path wrote
  `submitted_patch.v` directly into `work_dir` before anything had
  created that directory — every prior test of this code path (in
  `scratch_verify/verify_agent_module.py`) happened to reuse a scratch
  directory that already existed from earlier manual runs, which masked
  it. Fixed by creating `work_dir` at the top of `run_task()`, before
  any file is written into it (`rtlverdict/agent/loop.py`). Any real
  Phase 2 run against a fresh `results/agent_pilot/transcripts/` tree
  would have hit this same crash on its very first successfully-patched
  task, stub or real model.
- **Verdict wiring.** All 24 runs resolved to `PLAUSIBLE` — the *only*
  verdict a deterministic golden-revert patch can mechanically produce
  (BMC proves the submitted "fix" trivially equivalent to golden). That
  uniformity is the check: a single non-`PLAUSIBLE` result anywhere in
  this matrix would mean the ladder, the patch pre-check, or the verdict
  mapping is broken.
- **Resumability.** The full 24-run matrix was executed twice back to
  back in the same script invocation. Pass 1: 0 already cached (fresh
  output tree). Pass 2, immediately after: 0 run fresh, 24 found cached
  — the `_cached_trajectory` cache-hit path fired correctly against
  trajectories this same process had just written, not just against
  trajectories from a prior process.
- **Hard caps.** A dedicated task-arm run used a stub that never calls
  `submit_patch` (always calls the real `run_test` witness tool
  instead) with `max_iterations=3`. Result: `stop_reason=max_iterations`,
  3 iterations run, final verdict `NO-PATCH` — the cap tripped exactly
  where set and produced an explicit "didn't finish," never a
  fabricated verdict.

## 4. Cost / wall-clock actuals

**Cost: $0** — no API calls were made (`caps` below governs a real
run's ceiling, unused here). Config in force for the main matrix, for
the record: `max_iterations=15`, `max_tokens_per_turn=4096`,
`max_total_tokens=100000`, `max_wall_time_s=600`, `seed=0`.

Wall-clock is dominated entirely by the real BMC check on each
submitted patch (golden vs. golden, at the same per-design `k`/timeout/
`memory_map` used to build the corpus) — the stub itself returns in
effectively zero time.

| design | n | min | max | mean |

fabricated timing.

## 6. The testbench-passes-but-verdict-REFUTED question — not answered here

The original Phase 2 brief's central check — does an agent ever submit
a patch that passes the design's own testbench but is formally
`REFUTED` by verdict (the project's own thesis appearing inside its own
evaluation) — **requires a real model actually attempting a fix.** A
deterministic golden-revert stub cannot produce this signal in either
direction: it never attempts a genuine fix, so it can never produce a
plausible-looking wrong one. This remains fully open until §7 runs with
a real key.
